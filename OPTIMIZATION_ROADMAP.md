# Roadmap оптимизации Gustaw

## Зачем нужен этот документ

Этот roadmap описывает работу над производительностью локальной версии Gustaw.
Проблемы внешней доступности, DNS, TLS, Nginx и VPS разбираются отдельно и не
должны смешиваться с оптимизацией интерфейса.

Главное правило: сначала измеряем, затем меняем одну группу причин, после чего
повторяем те же измерения. Предположения и ожидаемые улучшения не считаются
результатом, пока они не подтверждены цифрами.

## Что такое Lighthouse

Lighthouse — лабораторный аудит страницы в контролируемых условиях. Он
моделирует устройство и сеть, записывает загрузку страницы и формирует отчёт.
Оценка Performance — не самостоятельная цель: важнее исходные метрики и причины,
которые Lighthouse показывает под ними.

Запускаем как минимум два режима:

1. Mobile — основной сценарий, с ограничением процессора и сети.
2. Desktop — дополнительный сценарий для сравнения.

Каждый замер выполняем несколько раз на одной и той же версии приложения.
Фиксируем медианное значение, потому что одиночный запуск может быть случайно
быстрее или медленнее.

### Категории Lighthouse

- **Performance** — скорость появления и готовности интерфейса.
- **Accessibility** — доступность для клавиатуры, скринридеров и пользователей
  с особенностями восприятия.
- **Best Practices** — типичные технические и браузерные проблемы.
- **SEO** — базовая пригодность страницы для индексации.

Категории Accessibility, Best Practices и SEO проверяем, но в этом roadmap
главный фокус — Performance и Core Web Vitals.

## Основные метрики простыми словами

### LCP — Largest Contentful Paint

Время, когда на экране появился самый крупный значимый элемент первого экрана.
Им может оказаться hero, большая фотография или крупный текстовый блок.

- Хорошо: до 2,5 с.
- Требует улучшения: 2,5–4 с.
- Плохо: более 4 с.

Сначала Lighthouse должен показать конкретный LCP-элемент. Нельзя назначать
всем изображениям высокий приоритет: это создаёт конкуренцию за сеть и способно
замедлить настоящий LCP.

### CLS — Cumulative Layout Shift

Суммарная величина неожиданных сдвигов интерфейса. Например, пользователь уже
видит страницу, а затем карточки резко перескакивают из одной колонки в три.

- Хорошо: до 0,1.
- Требует улучшения: 0,1–0,25.
- Плохо: более 0,25.

Текущее клиентское вычисление количества колонок — кандидат на источник CLS и
видимого «дёргания» сетки.

### INP — Interaction to Next Paint

Задержка между действием пользователя и следующим визуальным обновлением.
Например, насколько быстро реагирует кнопка лайка. В лабораторном отчёте без
реального взаимодействия Lighthouse может использовать вспомогательные
показатели, поэтому INP особенно полезно проверять на работающем сайте с полевыми
данными.

- Хорошо: до 200 мс.
- Требует улучшения: 200–500 мс.
- Плохо: более 500 мс.

### TBT — Total Blocking Time

Лабораторный показатель того, как долго главный поток браузера был занят
длинными задачами и не мог быстро реагировать. Помогает выявить тяжёлый
JavaScript и дорогую гидратацию.

- Хороший ориентир: до 200 мс.

### FCP — First Contentful Paint

Время появления первого содержимого: текста, картинки или другого элемента.
FCP не означает, что вся полезная часть страницы уже готова.

### Speed Index

Показывает, насколько быстро визуально заполняется страница. Полезен для общего
впечатления, но решения принимаем вместе с LCP, CLS и waterfall запросов.

### Transfer size и количество запросов

Сколько данных реально передано по сети и сколько отдельных запросов понадобилось.
Для медиагалереи эти цифры критичны: несколько лишних полноразмерных изображений
могут перевесить весь JavaScript приложения.

### Разбор JSON-отчёта запуска №3

- Lighthouse 13.4.1 применил симуляцию Mobile с RTT 150 мс и скоростью загрузки
  около 1 475 Kbit/s.
- Фактически в локальной записи FCP и LCP произошли через 131 мс, загрузка
  страницы завершилась примерно через 392 мс, а последний визуальный сдвиг —
  примерно через 153 мс.
- Значение LCP 26,8 с является результатом сетевой симуляции Lighthouse, а не
  фактическим ожиданием на быстром localhost.
- `cosmos-bg.png` передал 4 747 231 байт. При заданной Lighthouse скорости один
  этот файл требует примерно 26 секунд передачи.
- Аудит image delivery оценивает возможное улучшение LCP от оптимизации
  изображений примерно в 21 секунду.
- Всего передано 6 325 190 байт в 36 запросах. Изображения составили 5 975 109
  байт, то есть около 94,5% всего трафика.
- Фон составляет около 75% всей стартовой передачи страницы.
- JavaScript: 14 запросов и около 194 KiB; его выполнение заняло около 0,2 с,
  TBT практически нулевой. JavaScript не является текущим главным ограничением.
- Hero передан оптимизатором Next Image как файл около 108 KiB, но выбран
  неоправданно большой вариант; после правильного `sizes` Lighthouse ожидает
  около 86 KiB дополнительной экономии.

Причина расхождения между LCP breakdown и итоговым LCP установлена: breakdown
показывал фактически записанные локальные TTFB/render delay, а итоговый балл
использовал Lantern-симуляцию медленной мобильной сети. Это не зависание React и
не 27 секунд работы JavaScript.

и только затем подключаем выбранный вариант. Исходник не удаляется.

## Этап 3. Стабильная masonry-сетка

### Почему сетка сейчас сначала одноколоночная

`ImageGrid` не знает ширину окна во время серверного рендера. Начальное состояние
`columnCount` равно 1. После загрузки и выполнения JavaScript вызывается
`matchMedia`, состояние меняется на 2 или 3, после чего React заново распределяет
карточки по колонкам.

Это не обязательное поведение и не свойство masonry. Это следствие текущей
реализации через клиентское состояние.

### Что исследуем

- [ ] Измерить, создаёт ли перестроение заметный CLS.
- [ ] Проверить CSS columns или другую CSS-only раскладку без зависимости от
  `window` и без перестройки после hydration.
- [ ] Проверить порядок чтения карточек и доступность клавиатурной навигации.
- [ ] Проверить, сохраняется ли желаемый визуальный порядок фотографий.
- [ ] Сравнить сложность и производительность вариантов до замены реализации.

## Этап 4. Длинная лента и DOM

Lazy loading изображений и виртуализация решают разные задачи:

- lazy loading не скачивает изображение, пока оно далеко от viewport;
- виртуализация не держит далеко расположенные карточки в DOM.

Сейчас infinite scroll подгружает данные страницами по 9 элементов, но после
долгой прокрутки все ранее показанные карточки остаются отрисованными.

Порядок работы:

- [ ] Измерить DOM и использование памяти после 9, 90 и максимально доступного
  количества карточек.
- [ ] Проверить плавность прокрутки и длительность React-коммитов.
- [ ] Сначала оценить дешёвый вариант `content-visibility: auto`.
- [ ] Внедрять полноценную виртуализацию только при измеренной проблеме.
- [ ] Для виртуализации заранее решить вопрос переменной высоты изображений,
  восстановления позиции скролла и сохранения masonry-порядка.

Виртуализация не является первой оптимизацией: 181 карточка может потребовать её,
но решение должно опираться на DOM, память и плавность, а не только на число.

## Критерии готовности первой итерации

- LCP-элемент определён и получает ресурсы без лишней конкуренции.
- Фон и hero визуально сохранены, но передают существенно меньше данных.
- Мобильная карточка не получает неоправданно крупный исходник.
- Изображения ниже первого экрана не загружаются преждевременно.
- Сетка не делает заметного одноколоночного скачка после hydration.
- Повторные измерения выполнены в тех же условиях и записаны в таблицу.
- Изменения подтверждены production build и ручной проверкой интерфейса.

## Не входит в эту работу

- Перенос изображений из Cloudinary без отдельного решения.
- Удаление качественных мастер-изображений.
- Внедрение Redis или виртуализации только ради формального статуса
  «оптимизировано» без измеренной необходимости.
