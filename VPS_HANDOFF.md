# VPS Handoff: перенос приложения со скомпрометированного VPS

Актуально на 3 октября 2026 года. Этот файл создан как самостоятельный контекст для нового чата, который будет переносить другой проект — приложение о путешествиях — со старого скомпрометированного VPS на новый сервер. В новом проекте используется Docker и база данных находится на VPS.

Перед началом новый чат должен также прочитать `TABLE_BOOKER_MIGRATION_HANDOFF.md`: там описан параллельный перенос Table Booker и уже собран контекст нового VPS. Факты о конкретном travel-проекте нужно проверить в его собственном репозитории и на серверах; не считать стек Gustaw или Table Booker автоматически применимым.

## Задача нового чата

1. Найти и проверить репозиторий travel-проекта.
2. Провести read-only инвентаризацию старого VPS и определить все данные, без которых приложение не восстановится.
3. Развернуть приложение из проверенного Git-репозитория на новом VPS.
4. Перенести базу данных и постоянные Docker-данные, не перенося заражённую систему целиком.
5. Проверить приложение на новом сервере до изменения DNS.
6. Переключить домен с подготовленным откатом.
7. Проверить доступность и функции приложения с нескольких устройств и сетей.

Старый VPS скомпрометирован. Его следует считать недоверенным источником, пригодным только для извлечения необходимых данных и описания фактической конфигурации. Не переносить образ ОС, системные бинарники, неизвестные контейнеры, cron/systemd units, SSH-конфигурацию или весь `/etc` вслепую.

## Что реально произошло при переносе Gustaw

### Итоговая рабочая схема

- Новый VPS: `94.241.142.12`, Ubuntu 24.04.
- Проект: `/home/tapir/apps/gustaw-fin`.
- Ветка: `production`.
- Успешно развёрнутый релиз: `81572f0`.
- Next.js 15.3.6 слушает только `127.0.0.1:3100`.
- Процесс запускается systemd-сервисом `gustaw-fin.service`, а не PM2.
- Nginx принимает публичный HTTPS и проксирует запросы на локальный порт приложения.
- Локальная проверка через Nginx возвращает HTTP/2 200.

Перед деплоем ожидался PM2, однако `pm2` на новом сервере отсутствовал. Фактический родитель процесса был найден через PID/cgroup: `/system.slice/gustaw-fin.service`. Главный урок — не устанавливать новый process manager по старой документации, пока не выяснено, что реально управляет процессом.

### Как диагностировали запуск

Полезная последовательность read-only проверок:

```bash
git status --short
git branch --show-current
git rev-parse --short HEAD

pgrep -af 'next-server|next start|node|pm2'
ss -ltnp
readlink -f /proc/<PID>/cwd
cat /proc/<PID>/cgroup
systemctl list-units --all --type=service --no-pager | grep -Ei '<project>|next|node'
systemctl status <service> --no-pager
```

Эти проверки позволили найти настоящий каталог, порт и systemd unit без установки лишних инструментов и без остановки соседних приложений.

### Что случилось после успешного деплоя

Сборка прошла, сервис был `active`, локальный HTTPS возвращал 200, но браузеры показывали `ERR_TIMED_OUT`. Это оказалось не ошибкой сборки приложения.

- IPv4 работал: `curl -4 -I https://gustaw.ru/` возвращал HTTP/2 200.
- В DNS существовала AAAA-запись `2a03:6f01:1:2::2:12e7`.
- TCP по IPv6 устанавливался, но TLS зависал до тайм-аута.
- После удаления AAAA-записей DNS ещё некоторое время отдавал старое значение из кэша до истечения TTL.
- Когда публичный AAAA исчез, обычный `curl` заработал, но Chrome всё ещё использовал старое состояние даже в инкогнито.
- Safari и телефон уже открывали сайт. После очистки host cache и socket pools в `chrome://net-internals`, полного завершения Chrome и нового запуска сайт открылся.

Вывод: успешные build/service/local curl не гарантируют внешнюю доступность. Нужно отдельно проверять DNS, IPv4, IPv6, TLS и браузерный кэш. Удаление записи в панели не означает мгновенное исчезновение её из DNS-кэшей.

Это объясняет конкретный эпизод 3 октября. Нельзя автоматически сводить всю прежнюю нестабильность Gustaw только к IPv6: ранее наблюдались отдельные внешние TLS-сбои, подробно описанные в `SITE_AVAILABILITY_HANDOFF.md` и `SITE_AVAILABILITY_NEXT_STEPS.md`.

## Главные ошибки, которые нельзя повторять

- Не верить старой инструкции про PM2, путь, порт или пользователя без проверки текущего процесса.
- Не выполнять `git pull`, если в рабочем каталоге есть неизвестные незакоммиченные файлы. Сначала определить, кому они принадлежат и нужны ли приложению.
- Не переносить секреты в чат, git, логи или новый образ. Фиксировать только имена переменных и места хранения.
- Не делать `docker compose down -v`: ключ `-v` удаляет named volumes и может уничтожить базу.
- Не считать Docker volume резервной копией. Нужен отдельный логический dump БД и, при необходимости, отдельная копия volume/files.
- Не копировать весь Docker data root (`/var/lib/docker`) со скомпрометированного сервера.
- Не запускать миграции до резервной копии и понимания их направления/совместимости.
- Не публиковать порт БД наружу без необходимости. База должна быть доступна приложению через внутреннюю Docker network или localhost.
- Не переключать DNS до проверки нового сервера через нужный `Host`/SNI.
- Не добавлять AAAA только потому, что у VPS есть IPv6. Сначала отдельно проверить полноценный IPv6 HTTPS-путь.
- Не перезапускать Nginx, Docker и приложение как универсальное «лечение»: сначала собрать доказательства.
- Не принимать одну успешную загрузку за завершённый перенос.

## Этап 1. Локальный репозиторий и модель приложения

До работы с серверами новый чат должен прочитать `README`, `AGENTS.md`, Dockerfile/Compose-файлы, lockfile, миграции и deployment-документацию travel-проекта.

Нужно установить:

- точную ветку и commit для релиза;
- Compose-команду и список compose-файлов/профилей;
- используемые образы и их фиксированные версии;
- какой контейнер принимает HTTP и на каком внутреннем порту;
- тип и версию БД;
- где лежат migrations и какой командой они применяются;
- перечень named volumes и bind mounts;
- наличие пользовательских uploads/media вне БД;
- внешние сервисы: объектное хранилище, OAuth, почта, карты, аналитика и т. п.;
- обязательные переменные окружения без вывода их значений.

Локально выполнить тесты и сборку, предусмотренные самим проектом. Не придумывать команды до чтения `package.json`, Compose и CI.

## Этап 2. Read-only инвентаризация старого VPS

Сначала ничего не останавливать. Зафиксировать:

```bash
hostnamectl
uname -a
df -h
free -h
docker version
docker compose version
docker ps --no-trunc
docker compose ls
docker volume ls
docker network ls
ss -ltnp
systemctl list-units --all --type=service --no-pager
crontab -l
```

Для конкретного проекта определить:

- каталог checkout и `git remote -v`, branch, commit, `git status --short`;
- точную команду Compose и расположение `.env`/env files;
- контейнеры, health status, restart policy и published ports;
- образы и digest, а не только плавающие теги;
- БД: контейнер/внешняя служба, версия, имя базы и пользователь;
- named volumes, bind mounts и реальный объём данных;
- uploads, generated files, cron jobs, workers и очереди;
- Nginx virtual host, домены, upstream, лимиты загрузки и WebSocket-настройки;
- сертификат и способ его продления;
- текущие A/AAAA/CNAME, TTL и IP старого сервера.

Не печатать содержимое `.env`. Допустимо получить только имена ключей с аккуратным маскированием значений. Всё найденное на скомпрометированном VPS считать потенциально изменённым злоумышленником и сверять с репозиторием.

## Этап 3. План данных и согласованной остановки записи

Для базы на VPS требуется как минимум два экспорта:

1. Предварительный dump для проверки восстановления на новом сервере.
2. Финальный согласованный dump после остановки записи на старом приложении непосредственно перед переключением.

Для PostgreSQL предпочтителен логический dump подходящей версии (`pg_dump`/`pg_dumpall` в зависимости от задачи), для MySQL/MariaDB — соответствующий логический dump. Точную команду выбирать только после определения СУБД, версии, расширений и размера.

Перед финальным dump:

- объявить короткое окно обслуживания или перевести старое приложение в read-only;
- остановить workers/cron, способные писать в БД;
- проверить завершение активных операций;
- записать время начала и окончания;
- создать dump;
- проверить код возврата, размер и контрольную сумму;
- сохранить копию вне старого VPS;
- не удалять исходную БД после переключения.

Uploads и другие постоянные каталоги синхронизировать отдельно. Для большой директории полезен предварительный `rsync`, затем короткий финальный `rsync` после остановки записи. Не переносить исполняемые файлы и конфигурацию ОС вместе с пользовательскими данными.

## Этап 4. Подготовка нового VPS для Docker

Сначала проверить уже работающие приложения и свободные ресурсы: порты, память, диск, Docker networks, Nginx sites и имена контейнеров. Gustaw и Whiteboard на новом VPS нельзя останавливать общими командами.

Для нового проекта:

- создать отдельного непривилегированного пользователя/каталог;
- клонировать проверенный репозиторий;
- использовать отдельное Compose project name;
- закрепить версии образов;
- создать новые секреты и права на env-файлы;
- не монтировать Docker socket без доказанной необходимости;
- не использовать `privileged`, `network_mode: host` и широкие bind mounts без обоснования;
- добавить healthchecks для БД и приложения;
- настроить restart policy;
- ограничить журналы Docker, чтобы они не заполнили диск;
- публиковать HTTP upstream только на `127.0.0.1:<свободный порт>`, если впереди Nginx;
- не публиковать порт БД в `0.0.0.0`/`::`;
- проверить автоматический запуск Compose после reboot: systemd unit либо явно подтверждённая Docker restart policy.

Секреты старого скомпрометированного сервера по возможности заменить: пароли БД, session/auth secrets, deploy keys, OAuth/client secrets, API-токены и SMTP credentials. Ротацию планировать так, чтобы не лишиться доступа до завершения переноса.

## Этап 5. Пробное восстановление без DNS

1. Поднять БД на новом сервере.
2. Восстановить предварительный dump.
3. Поднять приложение и workers.
4. Применить только документированные production migrations.
5. Проверить healthchecks, логи и внутреннее соединение с БД.
6. Проверить Nginx-конфигурацию через `nginx -t` до reload.
7. Проверить сайт по доменному имени и SNI без изменения публичного DNS:

```bash
curl -4 -I --resolve example.com:443:NEW_IPV4 https://example.com/
curl -4 --resolve example.com:443:NEW_IPV4 https://example.com/ -o /dev/null -sS -w '%{http_code}\n'
```

Если сертификат ещё нельзя получить до DNS-переключения, использовать отдельный временный hostname или другой безопасный способ проверки, но не отключать проверку TLS в финальном тесте.

Проверить не только главную страницу: регистрацию/вход, чтение и запись данных, uploads, изображения, поиск, фоновые задачи, WebSocket/SSE, письма, OAuth callback и административные функции — только те, которые реально существуют в travel-проекте.

## Этап 6. Финальное переключение

Перед переключением подготовить письменный rollback:

- старые DNS-записи и TTL;
- старый рабочий commit;
- местоположение предварительного и финального dump;
- команда остановки/запуска только нужного Compose-проекта;
- способ вернуть старый upstream/DNS;
- критерий, при котором выполняется откат.

Затем:

1. Остановить запись на старом приложении.
2. Сделать и проверить финальный dump и финальную синхронизацию файлов.
3. Восстановить финальные данные на новом VPS.
4. Запустить новый Compose-проект и выполнить smoke-тест через `--resolve`.
5. Изменить только записи нужного домена.
6. Получить/проверить новый сертификат и автопродление. Не переносить приватный TLS-ключ со скомпрометированного VPS.
7. Не выключать старый сервер немедленно; оставить его изолированным и доступным для контролируемого отката, но не допускать расхождения записей между двумя БД.

## DNS, IPv6 и кэш: обязательная проверка

Перед добавлением AAAA подтвердить, что новый сервер действительно отвечает по IPv6 на 443 и TLS завершается:

```bash
dig +short A example.com
dig +short AAAA example.com
curl -4 -I --connect-timeout 10 https://example.com/
curl -6 -I --connect-timeout 10 https://example.com/
```

Если IPv6 не настроен или `curl -6` зависает, AAAA не публиковать. Наличие IPv6-адреса в панели провайдера не является проверкой HTTPS.

После изменения DNS проверять авторитетные серверы и несколько публичных резолверов. Удалённая запись может отдаваться до окончания TTL. Инкогнито не гарантирует новый DNS/socket state. Если `dig` и `curl` уже исправны, Safari работает, а Chrome нет, очистить в Chrome host cache и socket pools и полностью завершить браузер.

## Критерий завершения

Перенос считается завершённым только когда:

- новый сервер работает на зафиксированном commit/image digest;
- все контейнеры healthy и переживают reboot/restart;
- восстановленная БД содержит ожидаемые данные и новые записи сохраняются;
- uploads и фоновые процессы работают;
- Nginx, HTTPS и продление сертификата проверены;
- A-записи указывают на новый сервер, а AAAA либо проверены, либо отсутствуют;
- сайт проверен с компьютера в Chrome и Safari, с телефона через Wi-Fi и мобильную сеть; VPN фиксируется отдельно;
- выполнена серия повторных открытий и повторная проверка позже, а не одна успешная загрузка;
- проверены логи Nginx, приложения, контейнеров и БД без новых критических ошибок;
- сохранены финальный dump, контрольные суммы, старые DNS-значения и инструкция отката;
- старый VPS не уничтожен до явного подтверждения пользователя и отдельного решения о безопасной утилизации.

## Что передать в итоговый отчёт

- репозиторий, branch, commit и image digests;
- новый каталог и Compose project name;
- контейнеры, внутренние/published ports и healthchecks;
- systemd/restart-механизм;
- тип/версия БД, имя volume и время финального dump без секретов;
- перечень перенесённых uploads/volumes;
- Nginx site, домены, DNS A/AAAA и TTL;
- сертификат и автопродление;
- результаты функциональных и сетевых проверок;
- выполненная ротация секретов;
- точный rollback и оставшиеся риски.

## Ограничение этого handoff

Этот документ содержит подтверждённый опыт Gustaw и общий безопасный план, но не описывает фактическую архитектуру travel-проекта. Новый чат обязан сначала провести инвентаризацию его репозитория и старого VPS. Особенно нельзя угадывать СУБД, имена volumes, Compose-команды, порты, домен, миграции и допустимое окно простоя.
